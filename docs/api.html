Unified format¶

unified.py¶

The unified per-cell format: the stable contract between data sources and the import. The pipeline is Raw Data -> Unified Format -> Import; this module owns the right-hand seam of that arrow for per-cell attributes.

One row per H3 cell, keyed by h3_id. Any data source (COP30, a custom DEM, GEBCO, custom water, …) contributes columns; the import is a pure consumer that knows nothing about where the data came from.

Water model (see the data dictionary):

ele_m terrain/bed elevation, always real ground/seabed water_depth_m positive water-column thickness (0 = dry). surface = ele_m + water_depth_m water_type classification only (’’ = land), independent of geometry

Map h3_id -> veg_type by polyfilling the OSM vegetation polygons.

Restricted to cells in the area grid. On overlap the denser tag wins (_VEG_PRIORITY). Water exclusion is applied later in build_cell_rows.

apian_terrain.unified.landcover_cell_map(landuse, natural_areas, cell_id_set, resolution)[source]¶

Map h3_id -> landcover tag by polyfilling OSM landuse + natural polygons.

Restricted to cells in the area grid. natural (physical surface) overrides landuse (zoning) on overlap, and within a source the later polygon wins – good enough for cartographic cell colour. veg_type takes precedence over this map (applied by the caller).

apian_terrain.unified.build_cell_rows(cell_centres, features=None, veg_map=None)[source]¶

Assemble the BARE per-cell grid rows for the DB (pure; no I/O).

Only intrinsic cell facts are produced: h3_id, lon, lat, ele_m (RAW terrain elevation – the bed carve moved to the write-time derive), rot_z, radius_eq, is_pentagon. The columns derived from OTHER tables (water_depth_m/water_type from water_bodies, veg_type from vegetation, colours from face_colors, and the coast/slope fields) are NOT set here – they are computed at write time by tyrbuild._derive_cells_from_output so table edits are reflected in the written cells.csv. features/veg_map are accepted for call-site compatibility and ignored.

apian_terrain.unified.outward_ring(ring)[source]¶

Normalise a footprint ring for extrusion: unclosed, no consecutive duplicate points, CCW winding; [] for a degenerate ring (< 3 pts or zero area – collinear rings cannot extrude).

CCW is the winding the Blender extrude assumes: for CCW input the wall quads (base_i, base_i+1, top_i+1, top_i) face OUTWARD and the roof cap faces UP. Source rings arrive in either winding (OSM ways are unordered; WKB has no winding mandate) and ~45% of real footprints are CW, which inverts every normal in the mesh – and the Structures material maps its wall/roof textures by face normal, so inverted normals corrupt the texture. lon/lat vs projected XY does not matter here: the equirectangular import projection scales both axes positively, preserving orientation.

apian_terrain.unified.load_for_import(output_dir, area_id, progress=None, subset=None, data_dir=None)[source]¶

Reconstruct features_by_type for the import from the unified files.

Returns the same dict shape the import builds from the combined GeoJSON: a synthesized terrain feature (area meta + cells), plus structures (with bridges folded back in), streets and landmarks. No sea/water_body/vegetation features – those are per-cell attributes now.

output_dir / area_id name a REGION manifest – the sole owner of the data files. subset, if given, is a {cell_ids, area} trim (from read_subset_manifest): only those cells become Terrain Centres and OSM features are clipped to their exact outline (see _Region); its area bbox overrides the region’s for OSM trimming. custombuild.py – merge custom data into the unified per-cell format.

The download pipeline (process_area) is the DEFAULT source for every cells.csv column. This module lets custom data OVERRIDE individual columns: bring a CSV keyed by lat/lon OR by H3 id (at any resolution), and its values are mapped onto the area’s H3 grid (at the build resolution) and written into the chosen column.

Grid geometry (h3_id, lon, lat, rot_z, radius_eq) is NEVER overridden – it is derived from the bbox + resolution. Pure stdlib + h3; no bpy, so the CLI and the GUI can both use it.

apian_terrain.custombuild.interpolate_field(cell_map, domain, *, coords, radius_m, power=2.0, method='idw', anchor=False)[source]¶

Fill/spread in-domain cells from the measured source cells on the 2D metric plane, restricted to domain (an h3_id set) and radius_m of a source. coords maps h3_id -> (x, y) meters (metric_coords).

method=’idw’ – inverse-distance^power-weighted AVERAGE of the sources

within radius onto each empty cell; sources keep their value. For INTENSIVE fields; the grand total is NOT conserved.

method=’voronoi’ – Voronoi Distribution: each source’s value is spread

across the in-domain cells metric-nearest it within radius, weighted by each cell’s distance to the region boundary (half the gap to the nearest competing source), normalised so the region sum equals the source value (grand total conserved). The source cell is redistributed too – it keeps only its share.

method=’diffusion’– 2D heat-map fill: Gaussian-kernel-weighted average,

kernel sigma = radius_m / 2 (smooth taper to the reach edge). anchor=True holds measured cells exact (gaps add mass); anchor=False rescales the whole field to the measured total (melt, sources change).

Returns (filled_map, interp_ids): filled_map is cell_map with the computed cells added/overwritten; interp_ids is the set of previously-empty cells that received a value (the importer’s <field>__i mask).

Modular data layers¶

The additive, dispatched-by-kind data layers (The unified dataset format): the layer registry, the sparse time-series store, and the desktop DuckDB export path.

layers.py – the modular data-layer registry.

A data LAYER is anything baked onto the base terrain (aggregate metrics today; navigation / edges / labels later). Each layer declares a KIND, and the three stages that touch it – the exporter, the import-contract validator (here), and the Blender importer (blender/main.py) – all DISPATCH on that kind. So adding a new kind of data = register a validator here + a baker in the importer, with no change to any core loop.

The manifest carries layers: [{name, kind, file, spec}]. Legacy manifests (data_fields / feature_files / celldata_csv) are normalised into the same shape by manifest_layers, so every reader sees one uniform list and the format stays append-only: an older importer skips an unknown kind, a newer importer reads an older manifest. Pure module (no bpy) – unit-tested.

series.py – the cell_series data layer: a per-cell value that changes over a large, discrete set of timesteps, baked for FRAME-DRIVEN STEP playback in Blender.

Where a cell_field is one scalar per cell, a cell_series is one scalar per cell PER timestep. Storage is sparse (CSR) so the data load is proportional to the records that actually exist, not to (cells x steps): a cell with no record at a step simply isn’t stored. Gaps are permitted and mean NULL – the cell displays nothing at that frame (NOT 0). There is no carry-forward: a missing step and an explicit-null record are identical (_present = False).

On disk, per field. The bulky CSR blobs live in a per-region <area>_handlers/ folder (the header stores their names folder-prefixed); only the .json header sits at the region root, where the manifest points to it. Blob names carry a per-write <stamp>: a reader memmapping the previous blobs (the Blender series cache) makes an in-place truncate-write fail on Windows, so every write gets fresh names and the header flips the reference (superseded blobs are cleaned best-effort):

<area>_handlers/<area>_<field>_series.<stamp>.rowptr

int64[n_steps+1] – CSR row pointer; the records for step s are the slice [rowptr[s] : rowptr[s+1]]. This is the only index playback needs: O(1) random access to any step, so scrubbing is a seek.

<area>_<field>_series.cols int32[nnz] – the cell (column into the .cells order) of

each record, grouped by step then cell.

<area>_<field>_series.vals.<dt> the value of each record (dtype default float32). <area>_<field>_series.interp uint8[nnz] – OPTIONAL; 1 marks a record synthesised by

resample_series (time-axis interpolation) rather than measured. Absent when every record is measured.

<area>_<field>_series.cells the cell order, one h3_id per line (col index -> h3_id). <area>_<field>_series.json header: dtype, n_steps, n_cells, nnz, min/max, gap policy,

the file names, per-step time_labels, discontinuity stats.

‘linear’ – straight-line between the two bracketing observations (np.interp). ‘nearest’ – the value of the nearest observation in time.

Rules (agreed): a cell is NEVER extrapolated before its first or after its last observation (those grid steps stay NULL – the cell shows nothing there); a grid step that coincides with a real observation keeps the MEASURED value (flag False); a cell with a single observation is never interpolated (it contributes at most the one grid step that lands exactly on it). apian_terrain.terrain.fetch_h3_elevations(area_id, cell_centres, raw_data_dir, gebco_tile_dir=None, dem_tile_dir=None, topo_tile_dir=None)[source]¶

Fetch elevation for each H3 cell.

Default source is COP30 (plus GEBCO bathymetry for all-ocean tiles, and NASADEM via OpenTopography – key-gated – for cells still missing, e.g. GLO-30 restricted territories where the bucket answers 403; see _nasadem_fallback). Custom GeoTIFF overrides, most general last-resort first in the precedence:

  • dem_tile_dir (“unified” custom terrain): a valid pixel wins for ANY cell it covers, land or bed — the whole ground in one file.

  • topo_tile_dir (“split” custom terrain): a valid pixel applies where the unified dir has no coverage. Water-map cells may still be re-bedded from bathy_tile_dir later in the pipeline (see pipeline’s water section).

COP30/GEBCO are only fetched for cells not covered by the custom tiles or where the custom sample is nodata, saving downloads for fully-covered areas.

Adaptive sampling based on the relationship between H3 cell size and COP30 pixel size (~30m N-S, ~18-30m E-W depending on latitude):

  • res >= 12 (cells ~4-11m, SMALLER than COP30 pixels):

    Bilinear interpolation at the exact sub-pixel cell-centre position. Multiple adjacent cells share the same COP30 pixel but get unique interpolated values from the surrounding 4-pixel neighbourhood.

  • res <= 11 (cells ~25-174m, LARGER than or equal to COP30 pixels):

    Adaptive window mean. Window radius is scaled so the sampled area approximates the cell inradius. For res9 (~174m) this is roughly an 11x11 pixel window; for res11 (~25m) it falls to 3x3 or 1x1.

One HTTP fetch per tile regardless of cell count. Results cached on disk.

ponytail: do not change this sampling strategy without explicit approval.

apian_terrain.water.build_sea_polygons(sea_chains, lat_min, lon_min, lat_max, lon_max, had_reversals=False, structures=None)[source]¶

Build sea polygon(s) for the terrain bbox.

Strategy:

  • Closed chains (islands) are clipped to the bbox and added as land polygons, AND join the polygonize line work so the tidal channels around islands form faces of their own.

  • Open chains + closed rings are polygonized together with the bbox boundary to produce faces. apian_terrain.water.apply_water_depth_profile(cell_ids, polygon, surface_ele_m, *, ebp_a, depth_cap_m, custom_depth=None, gmrt_depth=None, base_depth=None, gebco_depth=None, bbox=None, cell_surface_eles=None)[source]¶

Assign per-cell absolute bed elevations from the unified bathymetry model.

Two ingredients, resolved per cell:

  1. base = min(A * x**(2/3), grid), where x is the cell’s metric distance to shore and grid is the UNMASKED-GMRT depth (multibeam blended into the GEBCO base – continuous, no seam), or GEBCO if GMRT is unavailable, or neither for inland lakes (pure EBP ramp). This gives a plausible, smooth nearshore-to-offshore profile.

  2. MASKED GMRT (gmrt_depth) – a genuine multibeam sounding – then OVERRIDES that base outright where present, so real deep features (dredged holes, scour channels) survive rather than being clamped away by the shallow nearshore EBP ramp.

So EBP only ever shapes cells with no real sounding; measured depth always wins.

The result is clamped to depth_cap_m (WATER_DEPTH_BY_TAG / SEA_MAX_DEPTH_M). Distance-to-shore uses the natural coastline: bbox-edge segments (both endpoints on the bbox boundary) are excluded when bbox is given so the profile is driven by real shore, not the map edge.

Parameters:

  • cell_ids (iterable of H3 cell-id strings for this water body)

  • polygon (Shapely Polygon/MultiPolygon defining the water body)

  • surface_ele_m (water surface elevation in metres)

  • ebp_a (EBP scale A for this water_type (config.EBP_PROFILE_A))

  • depth_cap_m (maximum depth (positive), clamps the result)

  • custom_depth ({cell_id: positive_depth_m or None} from user-supplied raster)

  • gmrt_depth ({cell_id: positive_depth_m or None} from GMRT)

  • gebco_depth ({cell_id: positive_depth_m or None} from GEBCO)

  • bbox (optional (lon_min, lat_min, lon_max, lat_max))

  • cell_surface_eles (optional {cell_id: surface_ele_m} (flowing water))

Return type:

dict mapping h3_cell_id -> absolute bed elevation_m

gmrt.py¶

Fetch GMRT (Global Multi-Resolution Topography) bathymetry for an area bbox from the keyless GridServer, and sample per-cell ocean depth.

GMRT merges real multibeam sonar surveys into a global base grid. We fetch TWO layers per area (fetch_gmrt_grid(…, layer=…)):

topo (UNMASKED) – continuous coverage (multibeam where surveyed, the

GEBCO-derived base elsewhere, smoothly blended -> no seam). Used as the offshore base, min’d with the nearshore EBP ramp.

topo-mask (MASKED) – real multibeam only, nodata off-survey. A value here

is a genuine sounding, so it OVERRIDES the base+ramp outright and real deep features (dredged holes, scour channels) survive rather than being clamped to the shallow nearshore ramp.

A NaN/nodata sample means outside/off-survey; a >= 0 sample means land. See water.apply_water_depth_profile for how the two combine.

Grids cached at raw_data_dir/gmrt/{area_id}_{layer}.tif.

globe.py – orthographic H3 globe geometry + index-based area selection.

The companion app’s area picker is a rotatable orthographic globe of H3 cells: you mark hexes at any resolution and expand them to a target resolution. All selection is pure H3 index traversal (cell_to_children / cell_to_parent) – no projection-based hit tests – so it behaves identically everywhere, poles included. The projection is only for drawing and for turning a click into a lat/lon (then an H3 index).

Pure numpy + h3 (no bpy / tkinter), shared by the GUI and the pipeline.

This is the true H3 geometry – accurate on an orthographic globe and on a Mercator map alike. Pure h3 + numpy.

apian_terrain.globe.polygon_cells(marked, target_res)[source]¶

Trace the union outline of the marked cells into a polygon, then fill it with target_res cells (h3shape_to_cells). The result follows the shape of the selection – L-shapes and holes survive – with a clean target-res tiling inside, instead of the ragged/fractal edge you get from expanding a mixed-res selection down the (non-nesting) H3 hierarchy.

cells_to_h3shape needs a single resolution, so a mixed-res selection is first normalised to its finest res (children approximate their parent). Handles disconnected selections (LatLngMultiPoly). Returns a set of ids.

local_pbf.py¶

Local PBF library: find PBFs in the PBF dir whose coverage covers the area.

The local library is scanned first. When nothing local covers the area, the missing regions are downloaded from Geofabrik (geofabrik.py) using the configured email address to identify us as a real user. A file’s coverage comes from its PBF header bbox, or from a bbox embedded in the filename (e.g. planet_6.939,43.508_7.898,43.961.osm.pbf).

Selection: the smallest single file that fully contains the area bbox wins (smallest is fastest to clip). If no single file contains it, a greedy smallest-first union of overlapping files is tried – the stitch itself (dedupe by OSM id, newest version wins, cross-file reference completion) happens in pbf_reader._write_extract.

Completed pipeline extracts (*_extract.osm.pbf) ARE first-class sources: they carry full reference-complete data for their bbox, and their coverage comes from the *_extract.bbox.json sidecar the pipeline writes alongside. Reusing a small local extract beats re-clipping a multi-GB region file for any area inside it. Only in-progress temp writes (*_tmp.osm.pbf) are skipped. An area never selects its OWN extract (exclude_area_id): a rebuild must re-clip from real sources – and the GUI purges that file right after this scan.
