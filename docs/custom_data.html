Custom data¶

The download pipeline is the default source for every cells.csv column and every feature layer. apian_terrain.custombuild lets you override individual columns or whole layers with your own files – this is how you bring population, temperature, or any other per-cell attribute, or replace the buildings/streets/water with a curated set.

You can drive it from the companion app’s Build (custom data) tab (Companion app (desktop GUI)) or call the module directly.

For overriding the pipeline’s own terrain sources with local GeoTIFFs, set the Custom Unified Terrain / Custom Topography / Custom Bathymetry fields in the companion app’s Global Inputs panel (see Configuration) – those are fed into the pipeline itself, not applied as a post-process override.

What can be overridden¶

Per-cell columns (custombuild.OVERRIDABLE_COLUMNS):

ele_m, water_depth_m, water_type, veg_type, r, g, b.

Feature layers (custombuild.OVERRIDABLE_LAYERS):

structures, bridges, streets, landmarks, water_bodies, sea.

Important

Grid geometry (h3_id, lon, lat, rot_z, radius_eq) is never overridden – it is derived from the bbox and resolution. Custom data only ever changes the values carried on the grid, never the grid itself.

Column overrides¶

Bring a CSV keyed either by latitude/longitude or by H3 id (at any resolution). Each chosen column reads one value column from your CSV; values are mapped onto the area’s H3 grid in two stages:

  1. Bin to a native cell. latlon keying bins each row with latlng_to_cell at a chosen custom data resolution (the binning granularity); h3 keying uses the row’s own id (its resolution is intrinsic).

  2. Remap to the build resolution. Coarser native cells broadcast to their children; finer cells aggregate to their parent; equal pass through.

Rows that land on the same cell at any stage are aggregated: the mean for numeric columns (ele_m, water_depth_m, r, g, b) and the mode (most common value) for categorical columns (water_type, veg_type).

The relevant entry points are apian_terrain.custombuild.build_override_map() (custom rows -> {h3_id: value}) and apian_terrain.custombuild.apply_overrides() (apply onto the cells.csv rows in place).

Example – override ele_m from a lat/lon CSV¶

A CSV like:

lat,lon,elevation
43.731,7.421,12.5
43.732,7.423,13.1

is applied with:

import csv
from apian_terrain import custombuild as cb, unified

rows = cb.read_custom_rows("my_elevation.csv")
overrides = {
    "ele_m": cb.build_override_map(
        rows, column="ele_m", value_col="elevation",
        key="latlon", build_res=12, native_res=12),
}

with open("monaco_cells.csv", newline="", encoding="utf-8") as f:
    cell_rows = list(csv.DictReader(f))
changed, counts = cb.apply_overrides(cell_rows, overrides)

with open("monaco_cells.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.DictWriter(f, fieldnames=unified.CELL_COLUMNS)
    w.writeheader(); w.writerows(cell_rows)

Layer overrides¶

A feature layer is replaced wholesale by your own GeoJSON FeatureCollection. apian_terrain.custombuild.apply_feature_override() validates the file is a FeatureCollection and overwrites <area>_<layer>.geojson with it, returning the feature count.

Additive data fields¶

The override path above rewrites existing cells.csv columns. To bring an arbitrary named field (population, jobs, temperature, …) without touching the spine, add it as a data layer instead: values are binned onto the grid exactly like an override, but written to a side-channel <area>_celldata.csv and declared in the manifest as a cell_field layer, so the importer bakes a <field> attribute (plus a <field>_present flag) without bloating the append-only CELL_COLUMNS contract. Each field aggregates with either sum (extensive counts, split when a coarse cell broadcasts to children so totals hold) or mean (intensive quantities). The entry point is apian_terrain.custombuild.apply_data_fields().

Interpolation¶

Measured data rarely covers every cell. A field can be filled (or spread) from its measured cells at build time, so the importer stays a pure consumer.

Conceptually, the measured cells are generators: interpolation turns that sparse set of points into a filled mask over the surface, painting each generator’s influence onto the empty cells within reach. An empty cell is the canvas being filled, so a cell that should hold a genuine 0 must carry an explicit 0 record – an omitted cell is no data (a fill target), not a zero source. (This is the same null-versus-zero rule the Time series layer uses.)

All methods treat the area as a 2D top-down plane (metric equirectangular distance between cell centres, never H3 grid steps), are restricted to a domain (all / land / water) and a radius_km metric reach, and record which cells were filled in a <field>__i flag column:

idw

Inverse-distance-weighted average onto empty cells; sources keep their value. For intensive fields (temperature, density). Totals are not conserved.

voronoi

Voronoi Distribution – each source’s value is spread across the cells metric-nearest it, weighted by distance to the region boundary and normalised so each region sums to its source. For extensive counts: the grand total is conserved.

diffusion

2D heat-map fill – each empty cell gets the Gaussian-kernel-weighted average of the measured cells within the radius (kernel sigma = radius/2), the closed-form heat equation on the plane. anchor holds the measured cells exact and only fills the gaps; melt (unanchored) rescales the field to conserve the measured total.

See apian_terrain.custombuild.interpolate_field() and apian_terrain.custombuild.reinterpolate().

Time series¶

A field that changes over time is a cell_series layer (The unified dataset format): one value per cell per timestep, for frame-driven step playback. In the companion app it is produced by the Output tab: build output.data (an h3_id STRING key, an event_ts axis, aggregate value columns) and Write -> files exports one series per value column – see Companion app (desktop GUI). Directly, the same files come from apian_terrain.series.build_series() + apian_terrain.series.write_series().

Playback is step-only – any smoothing between timesteps is done upstream. A gap is null: a missing (or explicitly null) record for a cell at a step displays nothing there, distinct from a real 0; interior gaps in a cell’s series are permitted but reported as a validation warning. When the timesteps are real datetimes the series is meant to drive the sun/sky to each step’s instant.

Note

Shipped (beta): the series format, its desktop export, AND the Blender playback consumer. Static per-cell fields bake onto the Data Carrier at import (every cell_field as a <field> FLOAT + <field>_present BOOLEAN POINT attribute, with the GN Data Carrier / Data Field / Field Min / Field Max inputs wired per modifier – see The unified dataset format), and frame-driven series playback streams the series onto the carrier at import: the series binds to the area’s Data Carrier (a 1:1 point-mesh clone of the Terrain Centres) as a live <field> attribute (plus a <field>_present mask, and an _interp mask when the series ships an .interp handler) that a frame-change handler repaints from the CSR handlers each frame – step s shows at frame data_start + s, where data_start is the data layer’s Data Start Frame (DATA_START_FRAME, default 1); at import the scene frame range is respanned to [data_start - 1, +steps) – one warmup frame before the series start (see “Rendering cell_series playback” below). The Terrain Centres and Terrain Surface carry no data attributes: their Geometry Nodes setups sample the carrier by index (the Centres’ point index, or the Surface’s _hex_cell), so the per-frame rewrite never touches the render meshes. When a node group exposes a Data Carrier object input, the importer sets it per modifier to the area’s own carrier (so multiple areas in one file each sample their own). On Blender 5.2 the displayed field is always the first baked field (the first entry of the carrier’s recorded field order): 5.2’s Named Attribute Name socket ignores linked strings, so the bundled node groups hardcode a STATIC _data_value (+ _data_value_present) read, and the importer mirrors the first baked field onto those alias attributes – the per-frame series repaint updates the mirror in lockstep. The Data Field string input remains wired for forward compatibility. Sun/sky coupling to each step’s datetime is a planned follow-up, not yet wired.

Rendering cell_series playback¶

Always render the scene frame range exactly as the bake set it: it starts one frame before the series start. That first frame is a warmup frame and its output (f_0000 with the default range) is junk – discard it. It exists because an animation render job evaluates with a fresh depsgraph that has no evaluation history: without a frame evaluating before the series start, a stateful Geometry Nodes chain (a Simulation Zone fade, for example) never ingests step 0 and the data layer renders one frame late for the whole job.

Two mechanisms make the render output land correctly; both are automatic and only active while a render job runs (viewport scrubbing is unaffected):

  • Read-ahead – during a render job the frame handler writes the next frame’s step, cancelling the one-frame delivery delay that a stateful GN chain introduces in a fresh render depsgraph.

  • Evaluated-read pull – a render_post handler reads the carrier’s evaluated attribute through the render’s own depsgraph each frame; without it, an in-flight render never re-syncs the carrier and every frame renders the state the file was loaded with (frozen).

tools/render_headless.py defaults to the scene’s frame range, so it includes the warmup frame automatically; with --start/--end of your own, include one frame before the series start and drop that output frame.

Resampling through time¶

Interpolation also runs along the time axis. Read the generator framing above the other way round: a cell_series is a stack of time slices, and any one slice is a set of generators for a surface mask. apian_terrain.series.resample_series() generates the other axis – each cell’s own timeline – by resampling its sparse observations onto a regular grid you define with start, end and interval (method linear or nearest).

It fills only a cell’s interior gaps: steps between that cell’s first and last observation. A cell is never extrapolated before its first or after its last value (those steps stay null), and a cell with a single observation is left untouched. A grid step that lands on a real observation keeps the measured value; only synthesised values are flagged, in a .interp handler the validator discloses. Opting a cell into resampling is the one case that overrides a gap displays nothing – for the interior steps it fills. As with the spatial mask, a cell that should read a genuine 0 between observations needs an explicit 0 record; the resampler will not invent one.

apian_terrain.tyrbuild.interpolate_output_data() composes both axes, time then space, on the companion app’s contract table output.data: it resamples every value column onto the shared grid, then – optionally – runs the spatial fill above on each resulting slice. The order is one-directional because the time pass is what aligns every cell to the same instants, which is what makes “the generators at this instant” well defined. It writes a new table output.<name> and leaves the source untouched, so re-runs are idempotent; every synthesised record stays flagged in __interp_<col> columns, which export carries into the series .interp handler. A spatial fill may give a value to a cell the time pass left null at the series’ ends – allowed, because a spatial value is supported by measured neighbours, unlike extrapolating a lone timeline off its own ends.

Note

The per-slice spatial pass runs once per grid step, so composing both axes suits modest step counts, not the largest (100k-step) grids.

Adding a brand-new attribute¶

Adding a column the format does not have yet (say population) is a small, deliberate change rather than an override:

  1. Append the column name to unified.CELL_COLUMNS (append-only – never reorder).

  2. Populate it in apian_terrain.unified.build_cell_rows().

  3. Read it on the Blender side as a cell attribute.

Because the CSV column order is an append-only contract, older readers keep working and new readers pick up the new trailing column.
