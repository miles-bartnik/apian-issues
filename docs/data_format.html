The unified dataset format¶

The unified format is the stable contract between data sources and the import: Raw Data -> Unified Format -> Import. Any source that can write these files can feed the Blender add-on, which is a pure consumer of them. It is produced by apian_terrain.unified (and the pipeline stages around it) and currently emitted alongside the combined <area>.geojson.

This page is the complete schema reference for every file the companion app writes – what each file is for, every column/key/property it carries, and which files are required versus optional. If you want to bring your own data, start with the file inventory below, then the per-file sections for the exact shape to match, then Custom data for the supported substitution paths.

File inventory¶

A dataset is a folder named after the area id <area> (the region root). Files marked always exist on every completed build; optional files appear only when the feature that writes them is enabled (or the layer is non-empty).

Region-folder layout: the region root holds IDENTITY files only – the manifest, cells csv, both metadata TSVs, the DuckDB, and custom_data/ (user imports). Everything derived lives in two subdirs: cache/ (per-region downloads and {area_id}-keyed caches: OSM/elevation/satellite) and output/ (the publishable geojsons/PNGs/color assets listed below).

The add-on’s importer is pointed at the manifest; it reads the identity files from the region root and the layer data files from the region’s output/ subdir, guarding each optional file with an existence check.

Subset manifests¶

A subset is a slim manifest (kind: "subset") that restricts an import to a chosen set of cells from a region (a full area manifest, which remains the sole owner of the data files):

{
  "schema_version": 2,
  "kind": "subset",
  "region": "monaco",
  "cell_ids": ["861f1a4d7ffffff", ...],
  "area": { ... trimmed bbox ... }
}

Think of it as SELECT cells FROM manifest WHERE cell IN subset.cell_ids: the subset names its region and the cells to bring in, nothing more – no data of its own. The importer takes the region manifest plus an optional subset and clips cells and features to the selection. Subsets are authored in the companion app’s Dataset Viewer (Companion app (desktop GUI)) and written by apian_terrain.unified.write_subset_manifest(); a subset is never a standalone dataset and is refused if opened as one.

Manifest¶

<area>_manifest.json (schema version 2):

{
  "schema_version": 2,
  "area_id": "monaco",
  "h3_resolution": 12,
  "area": {
    "lon_centre": ..., "lat_centre": ...,
    "lon_min": ..., "lat_min": ..., "lon_max": ..., "lat_max": ...,
    "ele_min_m": ..., "ele_max_m": ..., "ele_min_baked_m": ...
  },
  "cells_csv": "monaco_cells.csv",
  "n_cells": 123456,
  "feature_files":  { "structures": "monaco_structures.geojson", ... },
  "feature_counts": { "structures": 4912, ... },
  "attribution":  [ {"source": ..., "license": ..., "credit": ..., "optional": ...}, ... ],
  "image_texture": { ... },                // optional -- see Image Texture
  "data_fields":  [ ... ],                  // optional legacy cell_field block
  "celldata_csv": "monaco_celldata.csv",    // optional, with data_fields
  "layers": [ ... ]                         // optional data layers -- see below
}

The area block carries everything the import needs that is not per-cell – origin, bounding box, and the elevation floor used to derive scale – so the import can run from the unified files alone. ele_min_baked_m is the padded base plane below the lowest terrain (floor - pad_factor x range); the importer maps it to the bottom of the scene’s Z range.

The attribution block lists every data source the pipeline used, with its license and the required credit line, so a redistributed dataset self-documents its sources (see Data licensing). Entries flagged optional were only available if configured (GEBCO tiles, fallback elevation keys).

feature_files maps each layer name to its file name (all ten feature types are always listed and always written, even when empty); feature_counts is the matching feature count. A layer whose count is 0 is a valid empty FeatureCollection ({"type": "FeatureCollection", "features": []}).

Per-cell CSV¶

<area>_cells.csv has one row per H3 cell, keyed by h3_id. The column order is the contract – it is append-only and never reordered, so new attributes (population, temperature, …) are added as new trailing columns without breaking existing readers.

Column

Meaning

h3_id

H3 cell id (the key).

lon / lat

Cell centre, degrees.

ele_m

Terrain/bed elevation, always real ground or seabed.

water_depth_m

Positive water-column thickness; 0 = dry. Surface elevation is ele_m + water_depth_m.

water_type

Classification only ('' = unclassified: land, or water the simulation placed without a source-body tag), independent of geometry.

veg_type

Vegetation class ('' = none). Water always wins over vegetation.

rot_z

Cell rotation about Z (radians) for hex instancing.

radius_eq

Cell equivalent radius.

r / g / b

Per-cell colour, 0-255 (satellite for land, regolith for water).

coast_dist_m

Distance from the cell centre to the nearest shoreline (metres; static shoreline-wave field – see apian_terrain.coast). Scaled to Blender units at import (coast_dist_bu).

coast_dir_x / coast_dir_y

Unit vector pointing from the cell toward the shoreline (the direction waves travel). With coast_dist_m these drive shoreline wave animation without any per-frame geometry work.

is_pentagon

1 for the 12 H3 pentagons at each resolution (5 edges, not 6); only reachable at country/continent scale.

slope_x / slope_y

Bed-slope vector: least-squares gradient of ele_m over ring-1 H3 neighbours, in m/m, pointing uphill (over the seabed, toward shore) – see apian_terrain.coast. Written at import as the terrain_slope vector attribute (dimensionless, so never rescaled). With water_depth_m it drives shoreline wave shoaling, breaking and refraction steering.

The water model is intentionally orthogonal: ele_m is always the bed, water_depth_m is the column on top, and water_type is a label that does not depend on either. That keeps “where is the ground” and “how much water is above it” independent quantities. A cell can carry a water_type with water_depth_m == 0 (classification without resolved depth – wetlands and the shallowest shore cells).

Feature files¶

Discrete objects (buildings, bridges, roads, landmarks, water polygons) are one FeatureCollection per type, so a single layer can be swapped without touching the others. Vegetation is intentionally not a feature file – it is a per-cell attribute (veg_type). Every file is GeoJSON in WGS84 degrees ([lon, lat]); only streets and the combined terrain cells carry a Z.

Structures – <area>_structures.geojson¶

One Feature per building. Geometry: Polygon (CCW exterior ring, plus interior rings for courtyard holes; 2D, unclosed). Every property below is a top-level column in the output schema; there is no catch-all JSON blob.

Property

Meaning

feature_type

"structure".

structure_id

Stable id (osm_<id> / osm_r<relid> when not set).

osm_id

Source OSM id (string; r<relid> for relations).

source

"obm" (OpenBuildingMap) or "osm" when the footprint came straight from OSM geometry.

kind

Structure kind ("building" or "bridge").

notable

true for landmark/civic buildings (feeds the individual-object import path).

height_m

Building height in metres (tag, levels x storey height, or the default).

object_name / borough / suburb / usage

Optional user-defined display name and grouping columns.

primary_osm_tag / secondary_osm_tag

Primary/secondary OSM tag keys for this structure (e.g. building, historic, amenity).

name / historic / tourism / amenity / man_made / leisure

OSM label tags carried on notable buildings.

building_type

OSM building= value (yes omitted; null means generic).

wall_colour / roof_colour

Resolved wall/roof colours as #rrggbb hex strings (parsed OSM tag or the default).

wall_material / roof_material

OSM material strings (e.g. brick, tile). The Blender importer maps them to the material enum indices at load time.

roof_shape

OSM roof shape tag (e.g. flat, gabled). The Blender importer maps it to the roof-shape enum index at load time.

roof_type

Roof generation mode: generated, flat, or preserve.

roof_height_m

Generated roof height in metres (0.0 when roof_type is flat).

roof_direction_offset

Roof ridge direction offset in degrees from the footprint’s longest edge.

Bridges – <area>_bridges.geojson¶

Same shape as structures, split out for the deck-aware import path. A bridge feature additionally carries kind: "bridge" and deck: true (a man_made=bridge outline is the road-bearing deck). roof_shape is forced to "flat" and group to its own osm_<id>.

Streets – <area>_streets.geojson¶

One Feature per road/track way. Geometry: LineString with [lon, lat, z] per node – z is the terrain elevation in metres, draped from the cell the node falls in (tunnels and bridge spans run a straight grade between their span endpoints instead of draping). Properties:

Property

Meaning

feature_type

"street".

street_type

The street class: the OSM highway= value (motorway, residential, …) or a custom class (rural, fire_trail, circuit, industrial). Older files call this highway_tag – readers fall back to it.

width_m

Carriageway width in metres (tag-derived or the tag default).

tunnel

true when the way is a sub-grade tunnel.

bridge

true when the way is a bridge span/deck.

osm_id

Source OSM way id (string).

area_id

Owning area id.

Landmarks – <area>_landmarks.geojson¶

One Feature per named landmark (hospitals, museums, castles, towers, stadiums, named places, …). Geometry: Point. Properties: feature_type ("landmark"), name, category (the OSM key group, e.g. historic), tag (the specific value, e.g. castle), importance ("major" / "minor"), and landmark_type (integer class: 0 = major, 1 = minor). Both classes are written; the add-on panel filters minor landmarks via its Class dropdown.

Water bodies – <area>_water_bodies.geojson¶

One Feature per standing/flowing water body (lake, reservoir, river reach, harbour, dock, wetland, …). Geometry: Polygon (closed exterior ring plus interior island rings). Properties:

Property

Meaning

feature_type

"water_body".

water_tag

The classification (lake, reservoir, river, harbour, dock, wetland, …).

ele_m

Water surface elevation (metres; mean of the cells for standing water, per-cell terrain for flowing water).

depth_m

Maximum resolved depth inside the body (metres).

depth_source

Where the depth came from: gmrt (multibeam sounding), gmrt-base (blended grid), gebco+ebp (grid + beach profile), or ebp (pure equilibrium beach profile).

osm_id / osm_type

Source OSM element.

touches_bbox

true when the body was clipped by the area bbox.

Name

Display name (<area> - <water_tag>).

area_id

Owning area id.

(The pipeline-internal water_cells array is stripped before writing; per-cell water is on cells.csv instead.)

Sea – <area>_sea.geojson¶

The open-sea polygon built from the OSM coastline (bbox minus land). Geometry: Polygon (exterior plus island holes). Properties: feature_type ("sea"), sea_index (0 – multiple sea polygons are merged into one feature at import), depth_m (maximum resolved sea depth), plus the standard Name / area_id.

Natural Earth layers – <area>_ne_*.geojson¶

Country-scale fallback content, populated only when the area was built with detail mode Major features (at that scale the OSM structures/streets/landmarks layers are replaced by Natural Earth). At city scale these files exist but are empty.

File

Geometry

Properties

<area>_ne_urban_areas

(Multi)Polygon

feature_type ("ne_urban_area"), Name, area_sqkm.

<area>_ne_places

Point

feature_type ("ne_place"), Name, scalerank, pop_max.

<area>_ne_major_roads

(Multi)LineString

feature_type ("ne_major_road"), Name, road_type, scalerank.

<area>_ne_landmarks

Contour lines – <area>_contour_lines.geojson¶

Present only when a minor contour interval > 0 was set. One Feature per shared hex edge that straddles an elevation band; segments are the cells’ own boundaries, so lines align exactly with the hex terrain. Geometry: LineString (2 points). Properties: feature_type ("contour_line"), level_m (the contour elevation), is_major (true on index contours when a major interval was set).

Colour – <area>_color.geojson¶

Per-face colour samples: one Point Feature per (cell, face) – face 0 is the cell centre, 1..N the ring sectors (in edge-midpoint order). The point geometry is the sample location (handy in QGIS); properties carry h3_id, face and r / g / b (0-255). The importer bakes these onto the Terrain Centres as vectors; face 0 duplicates the cells.csv r/g/b.

The combined <area>.geojson¶

The legacy bundle: one FeatureCollection holding all of the above features (same per-type shapes) plus a single synthetic terrain feature. The unified files are the contract; the combined file is written for compatibility and for quick inspection. The terrain feature’s geometry is null and its properties are the area-level block:

{
  "feature_type": "terrain", "Name": "<area> - Terrain", "area_id": ...,
  "extend_km": ..., "n_lat": 0, "n_lon": 0,
  "lon_centre": ..., "lat_centre": ...,
  "lon_min": ..., "lat_min": ..., "lon_max": ..., "lat_max": ...,
  "ele_min_m": ..., "ele_max_m": ..., "ele_min_baked_m": ...,
  "h3_resolution": 12,
  "cells": [[lon, lat, ele_m, rot_z, radius_eq, h3_id, water_type,
             r, g, b, veg_type, water_depth_m, coast_dist_m,
             coast_dir_x, coast_dir_y, is_pentagon, slope_x, slope_y], ...]
}

Image Texture – <area>_image_texture.png + the image_texture block¶

When Image Texture is on, the raw tiles are stitched into one Web-Mercator-aligned PNG mosaic and the manifest records it:

"image_texture": {
  "file": "monaco_image_texture.png",
  "extent": {"zoom": 17, "tx0": ..., "ty0": ...,
             "width": 5120, "height": 4864,
             "lon_min": ..., "lon_max": ..., "lat_min": ..., "lat_max": ...},
  "source": "s2", "passes": 3
}

The extent maps pixel coordinates to lon/lat (its lat_max is the image’s top edge); the add-on UV-maps the PNG onto the Terrain Surface from it. Deleting the PNG orphans the block – the importer drops a missing texture silently.

Legacy manifests (built before the rename) carry the same block under the surface_texture key with a <area>_texture.png file; readers accept both spellings and always take the file name from the block’s file value.

Data layers¶

Beyond the per-cell spine and the feature files, a dataset can carry optional, additive data layers – extra attributes baked onto the terrain. The manifest lists them in a layers array, and every stage (exporter, validator, importer) dispatches on the layer’s kind:

"layers": [
  {"name": "population", "kind": "cell_field",  "file": "monaco_celldata.csv",         "spec": {...}},
  {"name": "footfall",   "kind": "cell_series", "file": "monaco_footfall_series.json", "spec": {...}}
]

The list is append-only: an older importer skips a kind it does not know, and a newer one still reads an older manifest (legacy data_fields / feature_files blocks are normalised into the same shape by apian_terrain.layers.manifest_layers()). Each kind’s import contract is checked by its own validator via apian_terrain.layers.validate_layers(), so adding a kind is a validator plus a baker with no change to the core loop.

cell_field – one scalar per cell¶

A named numeric field carried in <area>_celldata.csv (an h3_id column plus one value column per field; sparse – a blank cell is no-data). A field filled by interpolation also gets a <field>__i flag column (1 where interpolated); a conserving method additionally snapshots the original measured values in <field>__m. The importer bakes each field onto the area’s Data Carrier (a 1:1 clone of the Terrain Centres point mesh – point index N is cell N) under its bare name – <field> float plus a <field>_present boolean – so a consumer can tell a real value (including 0) from no-data. Nothing carrying a user field name is prefixed. The leading underscore is the reserved system prefix for the add-on’s OWN mesh attributes: _hex_cell (the shared cell index, same value space as the Terrain Surface’s _hex_cell face attribute), _terrain_color_* and friends on the Centres/Surface, and every other importer-baked attribute. User field names must not start with _ (the registration contract rejects them). The Terrain Surface joins the carrier by _hex_cell (Sample Index) in Geometry Nodes. The manifest data_fields array holds each field’s metadata (name, key, aggregation, units, min, max, count), with celldata_csv naming the file.

Note

Shipped: the Apian Terrain importer builds the area’s Data Carrier at import time whenever the manifest declares data layers, bakes every field found in the celldata as <field> (FLOAT) + <field>_present (BOOLEAN) POINT attributes (no per-field special cases), and – when a node group exposes a Data Carrier object input – sets it per modifier to the area’s own carrier, so one shared group stays area-agnostic. A generic consumer group selects the field through a Data Field string input (Named Attribute lookup; the importer defaults it to the first baked field) with Field Min / Field Max float inputs fed from the manifest data_fields metadata for normalisation. On Blender 5.2 the displayed field is always the first baked field (data_fields``[0]): the 5.2 Named Attribute node has no drivable Name socket (a linked string is ignored), so the bundled APIAN_TERRAIN_CENTRES/SURFACE groups read the STATIC ``_data_value / _data_value_present attributes, and the importer mirrors the first baked field onto them at bake time. The generic <field> attributes and the Data Field string input remain wired for forward compatibility. Frame-driven cell_series playback ships too (see below); its per-frame repaint keeps the _data_value mirror in sync.

cell_series – one scalar per cell, per timestep¶

An animated time series for frame-driven step playback, built to scale to millions of cells over tens of thousands of steps. Storage is sparse (compressed sparse row), so the on-disk size is proportional to the records that actually exist, not to (cells x timesteps):

File

Contents

<area>_<field>_series.json

Header: dtype, n_steps, n_cells, nnz, value min/max, gap policy, per-step time_labels, discontinuity counts, file names.

<area>_<field>_series.rowptr

int64[n_steps+1] row pointer: step s’s records are the slice [rowptr[s] : rowptr[s+1]].

<area>_<field>_series.cols

int32[nnz] – the cell (index into .cells) of each record.

<area>_<field>_series.vals.*

Each record’s value (float32 by default; float16 opt-in for known small-range fields).

<area>_<field>_series.cells

Cell order: one h3_id per line.

Timesteps are discrete – any interpolation between them happens upstream, so a consumer only ever steps. A gap means null: a cell with no record at a step (or an explicit-null record) displays nothing there, kept distinct from a real 0. Where the time_labels are real datetimes, the series is meant to drive the sun/sky to each step’s instant as well. Produced by apian_terrain.series.write_series() (and the DuckDB path apian_terrain.tyrbuild.export_cell_series()); see Custom data.

Note

Shipped (beta): the series format, its desktop export, AND the Blender playback consumer – per-field cell_field baking, the Data Carrier wiring (see above), and the per-frame cell_series repaint from the CSR handlers all ship.

The cell_series format is stable and produced by the pipeline today; the consumer plays it back by repainting a live <field> attribute from the CSR handlers on every frame change – the series stays off-mesh in its mmap’d handlers, so resident memory tracks only the current step. The repaint targets only the Data Carrier object, never the Terrain Centres/Surface render meshes (which sample it by index). A subset import (0.9.7) trims the series in memory to the subset’s cells before streaming, so a master series over the whole region serves any subset without re-export. Sun/sky coupling to datetime-labelled steps is a planned follow-up.

Companion app files¶

Outside the dataset folder, the companion app maintains:

The two metadata TSVs follow the tyr schema (the editable data-engine the Data Manager wraps); the app reads them back through apian_terrain.tyrbuild, so edits made in the grids and edits made by hand round-trip.

Bringing your own files¶

Three supported substitution paths, in increasing order of commitment:

  • Column overrides – your own CSV mapped onto the grid for an existing cells.csv column (ele_m, water_depth_m, water_type, veg_type, r/g/b).

  • Layer overrides – your own GeoJSON FeatureCollection replacing a whole feature file (structures, bridges, streets, landmarks, water_bodies, sea), matched against the per-type schema above.

  • Data layers – arbitrary named fields/series alongside the spine (celldata.csv / cell_series), so the append-only CELL_COLUMNS contract is never touched.

Custom data walks all three with examples. Grid geometry (h3_id, lon, lat, rot_z, radius_eq) is never overridable – it is derived from the bbox and resolution.

Reading a dataset¶

apian_terrain.unified provides the readers, including apian_terrain.unified.load_for_import(), which reconstructs the in-memory features_by_type structure the Blender importer builds from (a synthesized terrain feature carrying the cells, plus structures with bridges folded back in, streets and landmarks).
