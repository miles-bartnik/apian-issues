Design decisions¶

Why Apian is built the way it is. Each decision below is paired with the concrete constraint that forced it – not just what was chosen, but why the obvious alternative was worse. A handful of these are load-bearing (the two-halves split, the unified-format seam, the H3 grid); most other choices fall out of them. They are all applications of the project’s Values.

Two halves: a pure-Python pipeline and a pure-importer add-on¶

All fetching, fusing and geometry work lives in apian_terrain/ (plain Python). The Blender add-on under apian_terrain/blender/ only reads a finished dataset and builds objects – no downloads, no computation.

  • Blender’s bundled Python is a hostile place to do geospatial work. The heavy stack (rasterio, shapely, h3, osmium, boto3, pyproj) is painful to install into Blender’s version-locked interpreter. Keeping compute out means the add-on ships tiny – just the importer plus version.py and unified.py – and its only in-Blender dependencies are numpy/scipy.

  • It makes the logic testable without Blender. The tests are forbidden from importing bpy; because all the real geometry lives in pure modules, pytest can cover it directly. If computation lived in the importer, none of it would be reachable by CI.

  • “Importer is read-only” is an enforced invariant, not a style preference. The moment the add-on starts computing values, you get two divergent code paths (Blender vs. CLI) that silently disagree. A pure consumer means exactly one source of truth for every value.

A stable unified format as the seam¶

The pipeline emits a manifest + one per-cell cells.csv + one GeoJSON per feature type. The contract is Raw Data -> Unified Format -> Import (see The unified dataset format).

  • It decouples producer from consumer. Anything that can write the format can feed the add-on – which is exactly what makes Custom data (population, temperature, curated buildings) possible without touching the importer.

  • The CSV column order is an append-only contract. New attributes are added as trailing columns, so an older reader keeps working and a newer one picks up the new column. The data model can evolve without migration code scattered through every reader.

  • One GeoJSON per feature type means a single layer can be swapped in isolation – replace structures.geojson without disturbing streets or water.

Modular data layers dispatched by kind¶

Attributes beyond the fixed per-cell spine – interpolated fields, time series, future edge or label layers – are carried as data layers, each declaring a kind. The exporter, the import-contract validator and the importer all dispatch on that kind (see apian_terrain.layers).

  • Adding a new kind of layer touches no core loop. A new kind is a validator plus a baker; the manifest layers list is walked generically. The alternative – a growing if kind == ... in every reader – would couple every stage to every layer type.

  • The list is append-only, so the format stays forward- and backward-compatible. An older importer skips a kind it does not recognise; a newer one still reads an older manifest. No migration code – the same spirit as the cells.csv contract.

One output table, enforced by construction¶

The region database holds three schemas – source (raw file reads), staging (typed tables from the Data Manager’s metadata) and output, which contains exactly one table, data: an h3_id key, an event_ts time axis (a constant for a static snapshot), then one or more aggregate value columns.

  • The contract is enforced by construction, not inspection. The Output tab’s builder grid only generates the SELECT – value columns come from an aggregate dropdown, the key and axis from column pickers – so a malformed output.data cannot be authored through the app. Freehand SQL stays in the Query Engine console, which is read-only exploration. The one deliberate valve is a value column’s Custom SQL entry: a raw expression spliced into the generated GROUP BY query verbatim – outside the dropdowns’ enforcement, but inside the query’s shape (and it’s the user’s own database).

  • Interpolation happens in database-land, and honesty survives it. The Interpolation tab transforms an output table (time resample onto a shared grid and/or per-slice spatial fill) into a NEW output table – the source is never mutated, and every synthesised record carries a parallel __interp_<col> boolean that export turns into the series .interp handler / celldata __i flag. The measured-vs-filled distinction the format promises is preserved end to end.

  • The shape routes the export, not metadata flags. One distinct event_ts means a static dataset (the constant axis is dropped and the value columns become cell_field layers); more than one means a time series, exported as one cell_series per value column. The earlier routing keyed off a Data Manager checkbox whose name had to agree with the query’s output name – the same fact declared in two places is a drift trap.

  • Static is the degenerate case of series. Requiring event_ts even for a snapshot keeps one table shape for both kinds: “a series with one step” needs no schema of its own.

  • The grid’s resolution comes from the manifest, never from the user. The key is either binned from lat/lon at the manifest’s h3_resolution or an existing H3 column reconciled to it automatically: finer data rolls up via h3_cell_to_parent, coarser data spreads down over h3_cell_to_children – with SUM/COUNT split by child count so extensive totals conserve, and intensive aggregates broadcasting (the same convention the celldata remap uses). A free resolution picker would only ever author validation failures.

Time series: sparse storage, step-only, null means absent¶

A cell_series layer stores one value per cell per timestep for animated playback, built to scale to millions of cells over tens of thousands of steps.

  • Storage is sparse (CSR), not a dense grid. A dense (cells x steps) array reaches hundreds of gigabytes at the top end and spends most of that on empty cells. Storing only the records that exist makes the data load proportional to the actual data – the constraint that ruled dense storage out.

  • Playback steps; it never interpolates. Any smoothing between timesteps is done upstream, so the consumer only reads the current step – keeping it a pure consumer and the per-frame cost O(1) via the row pointer.

  • A gap means null, not zero. A missing (or explicitly null) record displays nothing at that step, kept distinct from a real 0 by a companion _present flag. Conflating the two would silently turn “no data” into a real measurement – the kind of quiet transform the project refuses to make. Interpolation reads this from the other side: the measured cells at any one step are the generators of a filled mask over the surface, and an omitted cell is a fill target, so a cell meant to read a true 0 must store an explicit 0.

  • Resampling along the time axis is an upstream, opt-in exception – and it is flagged. resample_series may synthesise a cell’s interior gaps (never its ends, never a lone observation), which is the one case that overrides “a gap displays nothing”; playback itself still only steps. Every synthesised record is marked in a .interp handler so it stays distinct from measured data, and the source series is never mutated – the resampled series is a new layer, so re-runs are idempotent.

H3 hexagonal grid as the spine¶

Everything bins onto an H3 grid; each terrain cell is an H3 id carrying attributes.

  • The hierarchy makes multi-resolution trivial. Custom-data remapping is just “coarser cells broadcast to children, finer cells aggregate to parent.” A raw lat/lon grid would need hand-rolled resampling; H3 gives it for free.

  • Cell ids are radius-independent, which keeps the door open to Moon/Mars/ fictional worlds – the body radius collapses to a single import constant rather than being baked through the whole pipeline.

  • Bulk classification runs in C. Sea and water-body fills use centroid polyfill (h3shape_to_cells) instead of per-cell point-in-polygon. At res 11+ over tens of km that is the difference between seconds and a wedged run.

  • Hexagons also sidestep the adjacency/orientation ambiguity of square grids – there is no diagonal-neighbour question.

The orthogonal water model¶

ele_m is always the bed (real ground or seabed), water_depth_m is the positive column on top, and water_type is an independent label. Surface elevation is ele_m + water_depth_m.

“Where is the ground” and “how much water sits on it” are genuinely independent quantities, and the earlier design that tangled them together caused recurring bugs – which is why this was a deliberate redesign. Keeping them orthogonal means flattening standing water, tapering depth, or reclassifying a cell each touch exactly one field and cannot corrupt the others.

Metres in the pipeline; Blender units derived once at import¶

The pipeline is metres-only (_m suffix). _bu (Blender-unit) values are produced at import from one field, Longest Edge (m).

Physical units are the honest representation for data; render scale is a presentation choice that should not leak into fusion logic. Deriving scale once from the bbox’s longest edge means areas of wildly different real-world size all arrive at a comparable on-screen size, controlled by a single number – and elevation can stay absolute for the multi-body case.

H3 cell-set selection replacing the rectangular bbox¶

Area selection moved from a lat/lon rectangle to picking a set of H3 cells on an orthographic globe.

The rectangular path carried a persistent rotated/transposed axis-swap bug. Pure-index cell-set selection made that entire class of bug disappear, and it is projection-correct at the poles and antimeridian where a naive bbox breaks. The redesign fixed a bug by deleting the thing that could be buggy.

Offline, local desktop app – no server, no telemetry¶

The companion app is a local window; only first-time data retrieval hits the network, after which tiles are cached on disk.

  • There is no product reason to run a server (single-user, local Blender workflow), and not running one removes an entire operational and privacy surface.

  • The whole pipeline can run against local data you already have. Nothing in the fusion logic requires a live service – point it at cached tiles and PBFs and it runs fully offline.

  • It survives services being shut down or moved to end-of-life. Because the network is only ever a first-fill convenience, no upstream provider going away can break an area you have already built, or one you have the source data for. If you have the app, it is yours forever.

This section is the sharpest application of the Perpetual Ownership value: the network is a convenience layered over a local alternative, never a dependency.

Satellite texture detail is Sentinel-2’s limit, not ours¶

A blurry draped texture over the Vila Franca do Campo islet prompted the suspicion that the z17 surface texture was being degraded somewhere between the tiles and the UV-mapped PNG. A side-by-side diagnostic (tools/_diag_zooms.py) stitched the cached z15 tiles, upscaled them 4x, and compared them against the z17 texture at the same extent: they are identical in information content.

The conclusion is that past z14 (Sentinel-2’s native 10 m/px at the equator) the Planetary Computer tiles are upsampled, not higher-resolution – the blur is the instrument, not the pipeline. sampling_zoom already caps at z17 for exactly this reason, and per-face colour alignment was separately verified (tools/_diag_faces.py). Any real detail gain for small features would require a genuinely higher-resolution imagery provider (a separate decision), not more zoom levels from the current one.

Decisions to not build things¶

Often the most revealing choices are the ones that were deliberately declined.

  • No structures-mode enum. A dropdown to switch building-construction modes caused a multi-session regression where structures came out empty. We reverted to extruded-only and made “keep it simple” an explicit rule: the added flexibility bought nothing a user asked for and cost real correctness.

  • Caves rejected as cells.csv columns / booleans. Caves break the heightfield assumption; the design landed on per-cell interval-stacks with per-edge wall deletion, and a boolean-geometry approach was explicitly considered and rejected. The grid-of-heights model cannot represent overhangs, so bolting it on would corrupt the clean per-cell contract.

  • No localized basemap tiles. Dropped because there is no free, no-key provider – a hard external constraint, not a technical one.

  • Vegetation is a per-cell attribute, not a feature file. It is areal and grid-aligned, so a veg_type column is cheaper and simpler than polygons, and it lets “water always wins over vegetation” be a trivial precedence rule.

Invalid OSM geometry: repair, don’t reject (and don’t die)¶

OSM rings occasionally self-intersect (terrace rows traced through a shared corner, stitching artifacts in multipolygon relations). At NYC scale this is a certainty: the 2026-09-21 new_york run died on exactly one invalid ring in 1,802,077 structures (relation r16243928, a self-touching figure-eight that is really two terrace houses). The policy, implemented by _safe_intersection in apian_terrain/pipeline.py and used by every clip of raw OSM geometry against the cell union (structure footprints, street ways):

  • Try the raw intersection first. Nearly every ring is valid; the repair path costs nothing unless it is needed.

  • On a GEOS failure, repair with ``make_valid`` and retry. make_valid (GEOS MakeValid) returns a valid geometry covering the same point set – for the ring above it recovers BOTH terrace houses (70.8 m2 total). This is the industry-standard repair (PostGIS ST_MakeValid, QGIS “Fix geometries”).

    The older buffer(0) idiom – still found in a few water/OBM sites – was deliberately NOT used for the guard: on the same ring it silently keeps one house and discards the other (37.1 of 70.8 m2 lost, no warning). Where the two disagree, make_valid preserves the data and buffer(0) can eat it.

  • On a second failure, skip the feature. The intersection result comes back EMPTY and the caller’s normal “nothing survives” path drops it. One malformed footprint can never kill a run again (regression test: tests/test_pipeline.py::test_clip_footprint_to_cells_repairs_self_intersecting_ring).

Deliberately deferred: user-settable invalid-geometry handling (min footprint area, repair-vs-reject, verbosity of repair reporting). The repair-by-default policy above is the agreed default; the tolerance knobs would slot in at structure-emission time (openbuildingmap._emit_osm) and be recorded on the structure record, not scattered through downstream stages.

Water flood preview: infinite vs finite heads¶

The water overlay preview contour-floods from fixed heads (one BFS, dam-aware – the cheap stand-in for the sim’s steady state). That approximation is only valid for water that cannot run dry. It treated EVERY fixed head as infinite, so a real hilltop pond – NYC’s Highlands have standing water at 50-174m, all legitimately mapped, terrain verified – flooded 92% of the region in the overlay while the actual sim (a budget fill with losses, which knows a pond runs dry) correctly wet ~11%. First exposure: NYC is the first area with standing water far above a huge connected lowland.

The classification is materialised at pipeline time as water_source_infinite BOOLEAN on output.water_cell_params (rules: tagged sea/ocean; sea-level surface AND water-connected to the sea through the bodies’ own cells; optionally body area >= WATER_INFINITE_MIN_AREA_KM2, off by default). The preview contour-floods infinite heads only; finite standing water wets exactly the cells its body is mapped over. The SIM is deliberately unchanged – its loss budget already limits finite sources, and the numbers validated it (sea-only flood 13,537 cells vs the sim’s 12,794 on new_york).

Coast distance was considered and rejected: it is not persisted in the DB, it conflates geographic nearness with ocean connectivity (a Great-Lakes-scale inland sea fails any distance test), and it adds a per-region magic constant. Connectivity + level needs no new data and classifies strictly better.

Known behaviour change: “dig a pit below a lake’s level and watch it fill” no longer previews instantly – it fills on the next sim run (the editor re-runs on Save). Infinite-reservoir preview next to the sea still works.

Companion fix (same incident): path-aware river inflow. The flat DEFAULT_RIVER_SOURCE_LPS (1000 lps per flowing body) could not pay the per-cell loss (5 mm/day over the full cell area) of a channel more than ~1 cell long at res 10 – 57 of 58 mapped NYC rivers ran dry in the sim. Each flowing body’s default inflow is now sized to its channel: path length (in cells) from the source to the nearest sea/edge head through the water graph, times per-cell loss, times a 1.5 margin, floored at the old flat default so short creeks are unchanged. Inland rivers (no water-path to the sea) are sized to wet their own channel. A lower bound, not a hydraulic solve.

Rivers follow real terrain — no course-following routing¶

Mapped rivers can look gappy (2026-09-21 NYC at res 10: dry cells inside river polygons) because the budget fill ponds still water against the real bed and route_streams walks real steepest descent; where the res-10 terrain bumps or the descent diverges from the mapped course, cells stay dry. Two fixes were considered and REJECTED in favour of honest physics: a sim-only channel carve (implemented then REVERTED — it barely moved the gaps, 735 → 765 gap edges, and worse it second-guesses the user’s own elevation edits under mapped rivers, breaking the editor contract at the exact spot users are told to hand-carve) and course-following routing (the walk sticking to the polygon’s cells), which would hard-code the answer and defeat the terrain editor’s purpose.

The documented position: the water simulation answers “what would water do on THIS terrain”. Accurate rivers therefore require accurate inputs — supply bathymetry (the pipeline’s custom bathymetry raster wins outright over GMRT/GEBCO for depths) or hand-carve the channel with the terrain editor’s elevation tools; both compose with the solver, because sim beds are the edited terrain (ele_m + offsets). Gappy mapped rivers on coarse DEMs are the simulator being truthful, not a bug.
