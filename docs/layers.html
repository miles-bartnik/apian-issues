Data Layers¶

Apian Terrain is assembled from data layers. Every layer is a real dataset with its own table(s) in the area database. Layers are either Core (required by every profile) or Optional (off by default, with a declared fallback). “Core vs Optional” is a profile default, not a different mechanism: Core layers are required=true layers, optionals are required=false layers. The staging/output contract gate (file_metadata.required, validate_staging_output) enforces presence.

Layer contract¶

Every layer declares:

  • Storage class — per-cell or feature (below); decides the key, the fallback semantics, and whether the editor can paint it.

  • Tables — declared up front; carried by the staging→output contract.

  • Required — true (Core) or false (Optional).

  • Fallback — what consumers see when the table is absent or failed. Must never break an export.

  • Provenance — which source produced each row: per-cell (cell layers) or per-feature (feature layers). Generalises the regolith-provenance idea to every layer; this is also what the UI shows (“this cell’s regolith: SoilGrids sand; climate: analytic fallback”).

  • Source & attribution — dataset version + license line, feeding the existing attribution plumbing.

  • Ingest entrypoint — --reingest-style refresh (CHELSA is the working template).

Storage classes¶

Per-cell layers — one row per cell (h3_id-keyed; face-keyed for imagery). Cell-level provenance, palette/default fallbacks, paintable in the Terrain Editor.

Feature layers — own geometry (points, polylines with width, polygons), surface-projected, not keyed by cell. Per-feature provenance (source tag). Fallback is absence (a missing feature renders nothing). Never painted per-cell; corrected via source data or feature edits.

Some layers are hybrids: a feature-class source table plus a derived per-cell table. The derivation can be a plain flattening (copy features into cells) or a physical solve. Water is the latter, and the distinction matters: its geojson features are initial conditions only — they define candidate water (bodies, sources, boundary levels) that preprocessing turns into per-cell parameters, but the simulation must always run to produce the true per-cell water state. The features alone never define where water actually is; the sim’s output does.

Layer map¶

project.cells is the wide per-cell materialization (published merged into output.cells with the editor’s edits.* overlay by rewrite_output — see the project-schema design, 2026-09-30): one row per cell carrying every layer’s propagated parameters (water flow/type, regolith material/seepage/depth, climate factors, vegetation type/density, ice thickness), so consumers read a single table. Layer tables are the system of record; each layer re-propagates independently when re-ingested. Editor overrides (edits.*) overlay at write time as today. Climate factors are SINGLE values (annualized), not monthly columns — seasonality is applied later by a deterministic mathematical climate model in Blender. Every propagated column carries a contractual definition (units, NULL/default semantics, provenance via the cells provenance map).

Future intake checklist¶

Every proposed layer answers, before it ships:

  1. Tier — Core, or which optional profile slot?

  2. Storage class — per-cell, feature, or hybrid?

  3. Capability unlocked — what user-facing thing becomes possible?

  4. Fallback — what do consumers see when it’s absent? (Never break export.)

  5. Cost — download size/time estimate, shown to the user before fetch.

  6. License/attribution — dataset version + credit line.

  7. Refresh path — the ingest entrypoint.

Users choose a profile (Core / Standard / Full), not individual layers; per-layer toggles live under an advanced fold. The general user should never see more than the profile choice.
